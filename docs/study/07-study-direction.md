# 07. 어떤 순서로 코드를 공부할까 — 수직 슬라이스 & 시작점 찾기

> 한 줄: **층(layer)별로 훑지 말고, 동작(=슬라이스) 하나를 위에서 아래까지 관통해라. 시작하는 쪽은 "방아쇠가 사용자냐(수동=UI출발) / 화면이 자동이냐(자동=DB출발)"로 정해진다.**
> 짝: [[00-flow-map]](읽기/쓰기 대칭 지도) · [[05-mutation]](쓰기 훅)

---

## 1. ❌ 층별 vs ✅ 슬라이스별

내가 물었던 순서: "service → hook → UI 순으로 공부하면 되나?"
→ 이건 **층(layer)별** 접근. 위험하다. 층끼리 따로 놀아서 "이 훅이 왜 저 서비스를 부르지?"의 **연결**이 머리에 안 남음.

```
❌ 수평(층별)            ✅ 수직(슬라이스별)  ← 이게 맞다
service 전부 보고        결제:    UI → hook → route → service → DB
hook 전부 보고           상품목록: DB → service → hook → UI
UI 전부 보고             장바구니: ...
```

- **슬라이스 = 동작 하나 = "~한다/~된다" 문장 하나.** ("결제 버튼 누르면 주문이 저장된다")
- 시니어가 새 코드베이스 파악하는 법 = **"이 버튼 누르면 무슨 일이 일어나지?"를 한 줄기 끝까지 따라가기.** 층을 훑지 않는다.
- 브랜치 이름 `docs/study-flow-trace` = 이미 이 방식으로 하고 있었음 (=trace, 관통).

---

## 2. "동작"이 뭐야?

프로그램에서 벌어지는 **사건 하나**. "~한다 / ~된다"로 끝나는 문장 = 동작 하나 = 슬라이스 하나.

| 동작 예시 | |
| --- | --- |
| 상품 목록이 **뜬다** | 동작 1개 |
| 결제 버튼 누르면 주문이 **저장된다** | 동작 1개 |
| 장바구니에 **담는다** | 동작 1개 |
| 상품 상세가 **열린다** | 동작 1개 |

---

## 3. ⭐ "시작되는 쪽" = 방아쇠를 누가 당기나

모든 동작엔 출발점(방아쇠)이 있다. **딱 두 종류.**

```
① 사람이 당김 👆  →  UI에서 출발
   "결제 버튼을 누르면 주문이 저장된다"
   └ 방아쇠 = 사람 클릭. 안 누르면 아무 일 없음.
   → UI(버튼)에서 시작해 서버로 따라 내려감

② 화면이 저절로 🔄  →  DB에서 출발
   "상품 목록이 뜬다"
   └ 방아쇠 = 페이지 진입하면 자동. 아무것도 안 눌러도 당겨옴.
   → DB에서 시작해 화면으로 따라 올라옴
```

### 던지는 질문 한 문장
> **"이 동작, 내가 뭘 눌러서 시작돼? 아니면 화면 뜨면 저절로 시작돼?"**

### ⚠️ "사용자 기준"의 함정
기준은 "사용자가 관련되냐"가 **아니다** — "사용자가 **방아쇠를 직접 당기냐**"다.
상품 목록도 결국 사용자가 보지만, **당겨와! 하고 누른 건 아님** → 방아쇠는 화면(자동) → DB 출발.

| 동작 | 방아쇠 | 출발점 |
| --- | --- | --- |
| 상품을 **주문한다** | 사용자 클릭 👆 | UI |
| 장바구니에 **담는다** | 사용자 클릭 👆 | UI |
| 상품 목록이 **뜬다** | 화면 자동 🔄 | DB |
| 상품 상세가 **뜬다** | 화면 자동 🔄 | DB |

---

## 4. 슬라이스 안의 방향 = 읽기냐 쓰기냐

시작점은 결국 [[00-flow-map]]의 읽기/쓰기 대칭과 같은 말이다.

**① 쓰기(Write) — 주문 = `usePurchase` (useMutation)**
사용자가 일으키는 일 → 트리거가 UI에 있음 → **UI에서 출발**해 내려감.
```
[버튼 클릭] mutate → usePurchase(fetch) → route.ts(POST) → createPurchase → DB
```
→ 실제로 세 파일에 UI→route→service 순으로 주석 단 것 = 무의식중에 "사용자가 시작하니 사용자 쪽부터" 따라간 것.

**② 읽기(Read) — 목록 = `useProducts` (useQuery)**
화면 뜨면 알아서 → 데이터가 DB→UI로 흘러옴 → **DB에서 출발**해 올라옴.
```
DB → service(select) → useProducts → 화면에 그림
```

→ "service → hook → UI"는 **읽기(GET)엔 맞고, 쓰기(POST)엔 거꾸로**다.

### 읽기 vs 쓰기 = 자동 vs 수동
| | 무엇 | 실행 방아쇠 | DB를 |
| --- | --- | --- | --- |
| **useQuery** | 읽기(GET) | **자동** (마운트) 🔄 | 안 건드림 (읽기 전용) → 백 번 새로고침 OK |
| **useMutation → `mutate()`** | 쓰기(POST/수정/삭제) | **명령해야** 실행 👆 | 바꿈 → 자동이면 들어가자마자 결제됨 😱 |

- `mutate()`는 "쓰기" 자체가 아니라 **쓰기를 시작하는 스위치**. (`useMutation`=배선만 / `mutate()`=발사)
- 방아쇠는 **꼭 사용자만은 아님**: 대부분 클릭(90%)이지만 `onSuccess`에서 코드가 부를 때도 있음(연쇄). → 본질은 "사용자냐"가 아니라 **"자동이냐 / 내가 불러야 하냐"**.

---

## 🔑 오늘의 핵심 한 줄
**층별로 훑지 말고 동작(슬라이스) 하나를 끝까지 관통하라. 시작점은 "방아쇠가 사용자 클릭(수동=쓰기=UI출발)이냐, 화면 자동(=읽기=DB출발)이냐"로 정해진다. 한 슬라이스를 완전히 씹으면 다음 슬라이스는 같은 뼈대의 반복 → 속도가 붙는다.**

## 📎 작은 개념 메모

### `crypto` — import 없이 항상 있는 내장 도구상자
`purchase.service.ts`의 `const paymentId = crypto.randomUUID()`.

```
crypto . randomUUID ()
──┬──   ────┬─────  ─┬
  │         │        └ () = 실행 스위치 (지금 켜!)
  │         └ 상자 안의 도구 (겹칠 일 없는 랜덤 UUID 생성기)
  └ 전역 내장 도구상자 (import 안 해도 항상 있음)
```

- **`import` 안 했는데 써진다** = 실행 환경이 미리 깔아둔 **전역(global)** 도구라서. (Web Crypto API 표준)
- **브라우저·서버 둘 다** 있음 → 그래서 서버 파일(service)에서 써도 OK.
  - 비유: 어느 집(브라우저 집/서버 집)에 가도 부엌에 기본으로 있는 칼. 챙겨갈(import) 필요 없음.
- `randomUUID()` → `"a1b2c3d4-...-1234567890ab"` 같은 36글자 랜덤 ID. 전 세계에서 겹칠 확률 극악 → **겹치면 안 되는 값**(`payment_id` = 주문↔PortOne 결제 잇는 열쇠 🔑)에 딱.
- ⚠️ 이름 함정: 요즘 방식인 **전역 `crypto`**(import 없이 바로 `crypto.randomUUID()`)와, 옛 Node의 `require('crypto')` 패키지는 이름만 같고 다른 얘기. import 안 떠도 "원래 되는 것".
