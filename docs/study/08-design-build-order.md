# 08. 설계와 개발 순서 — 뭐부터 만들까

> 한 줄: **읽을 땐 화면→아래로 거슬러, 만들 땐 아래(담을 곳)→화면으로 쌓는다. 설계는 코드가 아니라 "질문 5개"에서 시작하고, 황금 규칙은 "데이터 먼저, 화면 마지막".**
> 커링·persist 구조는 [[07-currying-create]] · 전체 데이터 지도는 [[00-flow-map]] · 서버 통로는 [[06-route-handler]] · 쓰기는 [[05-mutation]].

---

## 🧭 읽는 순서 ≠ 만드는 순서 (핵심)

```
읽을 때 (추적)   page → useCart → cartStore   (화면부터 거슬러 올라감)
만들 때 (개발)   cartStore → useCart → page   (담을 곳부터 쌓아 올림)  ⭐
```

**왜 바닥(담을 곳)부터?** page는 `addItem`이 **있어야** 쓸 수 있으니까. 불릴 것(로직)이 먼저 존재해야 부르는 쪽(화면)이 에러 없이 쓴다.

☕ 카페: 주방(cartStore) 없이 홀(page)에서 손님부터 받으면 만들 데가 없어 망함. → 주방 먼저.

**판단 규칙:** `"A가 B를 필요로 하나?" → B를 먼저 만든다.` = 의존성 화살표의 **반대 방향**으로 제작.

---

## 🎯 설계 5질문 (이 순서로 물으면 레이어가 나옴)

### 1️⃣ 무슨 데이터? 모양은?

```
장바구니 → 상품들, 각 상품 = { id, name, price, quantity }  (타입 CartItem)
주문     → 주문자 + 상품들 + 총액 + 상태
```

데이터 모양(타입)이 모든 것의 뿌리. 디자이너가 콘텐츠 먼저 정하고 레이아웃 짜는 것과 같다.

### 2️⃣ 어디 살까? — 클라이언트 vs 서버 (아키텍처의 절반)

```
잃어도 되는 임시 UI 상태  → 클라이언트(Zustand)   예: 장바구니, 모달 열림
영구·돈·보안 필요         → 서버(DB, Supabase)    예: 주문, 결제, 회원
```

- 장바구니 = 브라우저에만(임시). persist가 localStorage 백업.
- 결제·주문 = 서버 DB에 영구 저장 + **검증**.
- **돈은 브라우저를 못 믿는다** — 클라 값은 조작 가능(가격 1000→10). 그래서 서버에서 검증·저장.

### 3️⃣ 누가 쓰고, 누가 읽나? (흐름)

```
장바구니: page가 씀(addItem) → CartDrawer가 읽음(items)
주문:     page가 씀(mutate)  → 어드민이 읽음
```

쓰기/읽기를 나누면 필요한 함수가 보인다 (담는 함수 + 꺼내는 함수).

### 4️⃣ 레이어로 쪼개기 (한 층 = 한 역할)

```
🗄️  데이터층   DB 테이블 / 타입            "무엇을"
🔌  접근층     queries · Route Handler     "어떻게 읽고 쓰나"
📦  상태층     Zustand store               "지금 값은"
🔧  로직층     hooks (useCart 등)          "전달·가공"
🎨  화면층     page · components           "보여주기"
```

각 층은 한 가지만. `cartStore`=상태+로직, `useCart`=전달만, `page`=화면. 섞이면 나중에 지옥.

### 5️⃣ 만드는 순서 = 의존성 반대로

```
데이터층 → 접근층 → 상태층 → 로직층 → 화면층  (바닥부터)
```

---

## 🥇 황금 규칙

> **데이터 모양이 먼저, 화면은 마지막.**

화면은 자주 바뀌지만 데이터는 뿌리라서. 데이터를 잘 잡으면 화면은 갈아끼우기 쉽고, 거꾸로 하면 화면 바꿀 때마다 데이터가 흔들린다.

---

## 🛒 예: 장바구니를 0부터 만든다면

```
0️⃣ 설계     { id, name, price, quantity } 모양 정하기
1️⃣ cartStore  items: [] (담을 곳) + addItem (담는 로직)   ← 상태 먼저, 함수 나중
2️⃣ useCart    store.addItem 을 꺼내 전달 (로직 X, 전달만)
3️⃣ page       const { addItem } = useCart(); 버튼 onClick
4️⃣ CartDrawer 담긴 items 보여주기
```

한 층 쌓을 때마다 실제로 돌아가는지 확인 → 어디서 틀렸는지 바로 보임.

## 💳 예: 결제는 "담을 곳"이 다르다

원리는 같지만(담을 곳 먼저) 담을 곳이 **서버 DB**다.

```
0️⃣ 설계     주문자·상품들·총액·상태
1️⃣ DB 테이블  orders + order_items + purchases   ← 서버! (이미 설계됨)
2️⃣ 서버로직   Route Handler (/api/purchases) 생성·검증·웹훅
3️⃣ 클라훅     usePurchase · usePayment (mutate로 서버 호출)
4️⃣ 화면       page 결제 버튼
```

자세한 주문 데이터 모델은 별도 설계문서(docs/design/) 참고.

## 🔍 흩어진 파일 연결점 빠르게 찾기 (VS Code)

| 하고 싶은 것      | 단축키               | 뜻                      |
| ----------------- | -------------------- | ----------------------- |
| 정의로 점프       | **Cmd+클릭** / `F12` | "어디서 왔나" (거슬러)  |
| 사용처 모두       | `Shift+F12`          | "어디서 쓰나" (퍼져)    |
| 점프 후 복귀      | `Ctrl+-`             | 원래 자리로             |
| 파일 열기         | `Cmd+P`              | 이름으로                |
| 전체 텍스트 검색  | `Cmd+Shift+F`        | grep (누가 import 하나) |
| 파일 내 함수 목록 | `Cmd+Shift+O`        | 목차                    |

**import = 파일 사이의 다리.** 흩어져 있어도 `Cmd+클릭`으로 다리를 건너면 다 이어진다.
추적 순서: ① 화면에서 시작 → ② 함수 Cmd+클릭으로 정의로 → ③ import 따라 건넘 → ④ 길 잃으면 Ctrl+-.
